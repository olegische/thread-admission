# Per-call evidence example — editorial verification

Updated 2026-10-20. This note is outside the published article.

## Contract

The inference proxy observes individual requests and responses. It signs the complete ordered input and completed output for one call, using the API account from authentication and the response ID exposed to the agent. There is no thread ID, global offset, predecessor chain, per-item verification ID, or first-occurrence tracking.

Sections 5–6 demonstrate whole-item evidence with an operator index or a DSSE envelope. Section 7 distinguishes runtime thread, transcript, model context, and response output, then describes how the runtime selects evidence for an exported revision. Section 8 implements the component-evidence variant with SD-JWT.

The second call in the worked example receives `[user, call, result]` and emits `[answer]`. Its evidence therefore covers all four original example records as call content. Earlier context is repeated in the input rather than deduplicated into a proxy-maintained history. This does not establish that historical assistant items in that input were generated by earlier model calls, nor that this was the latest call in an external thread.

## Library and reproduction

Executed against Python 3.12, `sd-jwt==0.10.4`, `jwcrypto==1.6.1`, `jsonschema==4.26.0`, and `rfc8785==0.1.4`. The JCS dependency supports the whole-item index and DSSE paths; the SD-JWT library performs disclosure encoding and hashing.

```sh
uv sync --locked
uv run --locked python article/notes/check_sdjwt_example.py
```

The script extracts JSON fixtures and exact executable Python blocks from the current Markdown. The App Server transcript comes from section 1, the API call/result from section 5, the API answer from section 7 and the SD-JWT schema from section 8. No crypto or serialization mocking is used.

## Executed checks

- All article JSON and Python blocks parse; JSON object keys are checked for duplicates in fixtures.
- The whole-item record compares full input/output arrays, their lengths, order, item values, request/response membership, API subject and response ID.
- Real Ed25519 DSSE signing verifies the same per-call record. Modified envelope type or payload fails.
- Real ES256 SD-JWT issuance, holder presentation and verification reconstruct all selected claims for the second call. Five distinct 128-bit salts are held in client disclosures outside the signed JWT's clear claims.
- Altered values or salts, missing required disclosures, duplicate disclosures, changed signed fields, wrong API account, response ID, public key, type and future issuance time are rejected.
- The runtime adapter matches the two returned messages against authenticated claims, preserving which was observed in request or response and its index in that array. Changed, reordered or duplicated messages fail. Regenerated runtime IDs do not affect these comparisons.
- A client-supplied assistant item can be authenticated in the request without being labeled as generated response output. The test exercises this distinction explicitly.
- A separate earlier call verifies on its own, but fails when a different response ID is required. No cross-call chain is assumed.

Result: **43 rejection cases pass**, alongside the positive and explicit coverage-limit cases.

## Limits

The pinned reference library accepts extra unreferenced disclosures, contrary to RFC 9901 §7.1. The script reproduces that gap; production conformance is not claimed. It also leaves time checks to the application. This profile checks `iat` and issues no `exp` or `nbf`.

The text adapter leaves tool records, runtime IDs, and relative positions between messages and tools uncovered. Original tool components remain authenticated as received API content; that does not prove execution. A runtime-specific tool adapter must extract the selected values before those exported claims can be accepted.

A valid signed call is not proof of runtime thread membership, completeness, or latest revision. The receiving service checks the covered values before admission. A final response does not cover work added after it, and a summary in input does not authenticate the discarded originals. Delta-only input is outside the worked full-input path.

The ready SD-JWT package contains disclosures and therefore content. Delayed retrieval requires transient retention of the package. A no-content-retention proxy must deliver it at completion and rely on client storage, rather than promise later regeneration from hashes.

No live runtime or proxy round trip, deployment, full RFC conformance, or universal cross-format tool adapter was tested.
